# Subscription server-side compaction

## Decision and research

The bridge implements inline server-side compaction on its existing fixed subscription Responses endpoint. Harness local summarization stays in place by default; an opt-in agent preset replaces it for this provider alone, so Codex can own condensation without changing the stock installation.

The baseline `ea7abda40362be71080d36b527283304159b2958` did not send `context_management`, rejected compaction output items, and did not emit replay metadata. Its existing compaction evidence was for Harness text summarization.

[OpenAI's compaction guide](https://developers.openai.com/api/docs/guides/compaction) describes inline `context_management`, encrypted output items, and stateless input-array chaining with `store: false`. That public API documentation is not a guarantee of subscription-route availability. The [reference plugin v2.5.9](https://github.com/WSL043/dsh-codex-subscription/blob/v2.5.9/src/subscription-compaction.js) uses this mechanism on `/backend-api/codex/responses`. A real subscription session has since confirmed both halves: the route issued an encrypted compaction item once the request passed the then-shipped 32,768-token threshold, and the next request that echoed it back was priced at 11,787 input tokens instead of the 38,612 the same transcript had just cost. See [the verification record](VERIFICATION.md).

[Reference issue #152](https://github.com/WSL043/dsh-codex-subscription/issues/152) was closed without eliminating duplicate summaries. Its maintainer reported that suppressing local pressure compaction let the retained transcript grow beyond the model window, making model-switch recovery fail. Those experiments are the maintainer's evidence, not measurements from this implementation.

Harness 0.2.0-rc.2 has the necessary [replay envelope](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/packages/llm/llm/src/assembler.ts), but its [token meter](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/packages/llm/token-meter/src/index.ts) can prefer the full history estimate over a smaller provider usage report. Therefore cloud checkpoints and local summaries can both run by default: the meter prices the retained local surface, so the host still reaches its own threshold even when the wire request is compacted. This implementation does not patch the meter, change another provider, or inflate the model's disclosed window. The opt-in backend below replaces the host's automatic condensation for its own routes only; eliminating duplicate summarization in the default composition would need host recovery work, such as bounded chunked summarization.

## Enablement and request shape

Server-side compaction is always requested; the adapter has no configuration keys. Route compatibility cannot be checked locally, so the request is issued unconditionally and an explicit unsupported-parameter rejection falls back once to the original bounded request (see below).

With a disclosed context window of at least 2048 tokens, the request includes `context_management: [{ type: 'compaction', compact_threshold: floor(contextWindow × 0.95) }]`. 95% is the effective percent the subscription route's own client derives from its disclosed window, so compaction fires when context pressure is real rather than at a fixed byte-budget ceiling. The bridge has no tokenizer: the route compares its own rendered token count against the number sent here, and the byte bound below is a guard, not a token guarantee. Without a usable disclosed window, ordinary bounded requests continue without cloud compaction. No user-supplied threshold, destination, credentials, API-key route, `previous_response_id`, or standalone compact endpoint is introduced.

## Replacing local condensation (opt-in)

A profile can let this package's engine own condensation by enabling the agent preset it ships, `preset-codex-subscription`. The engine extends the host's stock engine and returns without condensing whenever the durable routed request belongs to `codex-subscription`; every other provider is delegated to the stock implementation unchanged, so the composition is route-scoped in behavior even though the preset is selected per session. [The installation guide](INSTALL.md) records the enable step, the post-mount checks and the failure modes.

The pinned Harness fixes where that engine has to live. Its `@deepseek-ai/dsh-web-app` bundle disables the top-level `compaction-basic` and `command-compact` rows and declares the backend inside each agent preset instead, in an isolated `compaction` group; a profile patch can override an existing row by id but cannot add one without an `insert:` list, and it cannot address an entry nested in a preset's `plugins` list at all. A preset is a complete declaration, so `presets/codex-subscription.patch.yml` restates the shipped standard composition with that one child's engine replaced. [The verification record](VERIFICATION.md) has the composition evidence and the `insert:` detail.

That row is inserted **disabled**: installing the package must not add a selectable preset to every profile, and a profile enables it with an id-keyed override in the profile patch. The Plugins page lists the row but locks its switch, because the Host unlocks only rows it can address through that patch. `scripts/sync-preset.mjs` derives the copy from the pinned Harness, so a Harness bump shows up as a small reviewable diff instead of an edit to a hand-maintained file; the profile verification path runs its `--check` mode, because a release that reshapes the `compaction` group would otherwise let double summarization return silently.

This is deliberately not enabled by default. The module subclasses a host-internal class, which is a compatibility dependency the bridge otherwise avoids: if that package disappears the preset fails its activation audit and stops composing, and if the reconciled method changes shape the override silently degrades to the stock behavior instead of breaking. Operators who enable it accept that coupling; the default installation keeps the stock backend and the duplicate summarization described above.

While the replacement is mounted, no local summary bounds the transcript, so the refusal and wire-budget behavior below is the only remaining recovery path.

### What the chat shows

The issuing turn carries a `Server-side compaction` marker naming the model and the replayed window's item count. It sits in the turn's work-details disclosure, like the chat's own local-condensation marker, so it follows the transcript-view setting rather than showing while every other detail is folded. It is derived entirely on the client from the assistant message's `replayState`, so it needs no session event: a reuse turn publishes nothing new and stays unmarked, and a refused window leaves the marker on the turn that originally published it. Refusals themselves stay in the host log, since a refusal is not durable in the session.

## State and validation

- Only successfully completed responses can publish replay metadata. Cancelled, failed, malformed and incomplete responses cannot publish a checkpoint.
- The latest compaction item and subsequent allowlisted output items form the next wire window. Subsequent text, reasoning metadata and function calls are retained; tools are never executed by this bridge.
- The streamed completed items are the authoritative output order. The live route omits items from `response.completed.response.output` — observed as a missing index once a real compaction was issued — so positional agreement with that array is not required. A terminal compaction item that exists and disagrees with the streamed one is still treated as a contradiction.
- An unprovable window is never published, and never fails the turn: the answer has already been delivered by then, so the first refusal label is logged and the bounded local history is resent instead. Refusals name their own stage (`ITEM_*`, `MSG_*`, `SUM_*`, `WINDOW_*`, `NO_ORDER`, `OBSERVE_DUPLICATE`, `COMPACTION_MISMATCH`, `CONTENT_MISMATCH`) from a bridge-owned vocabulary, so no response value reaches the log.
- Harness stores the bounded opaque window in the assistant message's `source.replayState.response.subscriptionCompactionV1`. The normal transcript stays intact. No separate bridge checkpoint file or process-global cache exists.
- Reuse binds to a hash of dedicated account routing headers and available subject/user claims, model, developer instructions and tool definitions, plus exact normalized input-prefix and assistant-content hashes. The newest checkpoint must match; older checkpoints are not searched as a fallback. Refresh with unchanged account routing does not itself invalidate it. Account/model changes, edits, local summarization, image offload changes and changed tools/instructions can invalidate it.
- Checkpoints expire after 24 hours, a conservative local policy, not a claimed backend expiration guarantee. Future timestamps and malformed/digest-mismatched metadata are rejected for reuse. Hashes detect inconsistency, not malicious forgery by trusted same-user code. Opaque content is never decoded or logged.

## Bounds and fallback

Checkpoint wire items are capped at 128 items, and the per-item and whole-window byte cap is the same derived value as the request bound: the threshold expressed in bytes at a conservative 8 bytes per token, with the original 512 KiB kept as the floor when no window is disclosed. A compaction window is a reduction of the input the route measured, and that input is bounded by the same value, so a window the route can produce cannot exceed the cap; the cap therefore guards stored state rather than limiting what the route may return. Existing SSE frame, aggregate response, timeout, admission and cancellation bounds still apply. The retained-history first pass allows at most 4096 messages, 4 MiB of text and 16 MiB of tool call/result text, so a checkpoint can replace an oversized covered prefix. The compacted wire request is bounded by the same window the threshold comes from, so a request can reach the threshold instead of being refused before the route has a chance to compact. The original 256 KiB text, 2 MiB tool-history and 1024-item bounds stay as the floor when no window is disclosed, and the model catalog lookup runs before validation because the bound depends on the disclosed window. Text and tool-history parts are each bounded by the derived value and the combined input is bounded by it too; the derived value is a guard, not a token guarantee. Covered images are not read or resent; uncovered images use the existing attachment and offload budgets.

If no valid checkpoint exists, the original full-history limits are reapplied. The newest persisted checkpoint is inspected on its own, and a refusal is named in the host log (`SHAPE`, `METADATA`, `EXPIRED`, `SCOPE`, `PREFIX`, `CONTENT`, `DIGEST`, a window stage such as `WINDOW_SHAPE`, or `INVALID` when the failure has no stage of its own) so a model switch, expiry or edited history stays distinguishable without logging opaque state. When a refusal leaves the full local history past the wire bounds, the turn fails with `COMPACTION_UNAVAILABLE` and asks for a new conversation rather than reporting the generic shape error. An HTTP 400/422 with a bounded structured error naming `context_management` and `unsupported_parameter` or `unknown_parameter` permits exactly one retry with ordinary, fully validated history and without the compaction parameter. There is no retry after partial output, arbitrary 400 errors, quota/authentication failures, network ambiguity or stream failure. An unrecognized checkpoint rejection is a safe fixed failure, not an automatic retry with potentially oversized history.

Recovery follows the official client, which removes the oldest history item when the window is exceeded while compacting instead of failing the turn. A window past its bound drops the oldest covered items, and the host log names the count. Only the covered window can be dropped: the uncovered tail is the live conversation, and the compaction item itself is what makes the window replayable. A persisted window is never trimmed, because trimming would change the digest it was proved against, so a stored window past the bound is refused whole. When nothing is left to drop, the turn is still refused rather than sent oversized, and limits are never raised silently. Keep Harness local summarization enabled. Even that does not guarantee it runs before this bridge's byte limits, because the host measures tokens, not UTF-8 bytes. Long-lived checkpoint-independent recovery remains an explicitly unresolved limitation.

## Verification and remaining work

Synthetic tests cover public Harness runtime dispatch, its actual block assembler, JSON persistence/replay, repeated turns, post-compaction tool results, history/account/model/instruction/tool invalidation, age checks, malformed and oversized items, terminal contradictions, missing tail items, cancellation, covered images, wire budgets, and the narrowly scoped parameter-rejection retry. `test/compaction-backend.test.mjs` pins the host engine class and checks that the opt-in backend skips only this provider, delegates every other route, survives a missing route or session, and names each refusal label. The packaged module is included in the normal tarball composition checks.

Automated tests make no real authentication or subscription calls. A manually driven Desktop session confirmed real checkpoint issuance and reuse on a dedicated login; [the verification record](VERIFICATION.md#real-account-evidence-and-limits) is the single list of what is confirmed and what is still open. The opt-in backend is checked at the module boundary against the pinned `@deepseek-ai/dsh-compaction-basic`, and its preset row is checked for shape, composition and drift. The enabled preset has since been exercised on a real account with an artificially low trigger: a subscription route past its threshold raised no local compaction, the same preset on another provider ran the stock engine, and `/compact` still condensed. Automatic pressure at the shipped bridge ratio (258,400 tokens for the 272,000-token Codex window) is now observed on a real account; [the verification record](VERIFICATION.md#window-ratio-pressure-on-a-real-account-2026-10-18) is the measurement.

After separate authorization, use an isolated profile and dedicated login for a bounded service experiment: verify issuance then reuse, cancellation and a local summary, with a fixed request/token budget and a stop condition. Record only sanitized counters and size measurements, never opaque checkpoints, credentials, account identifiers or raw authenticated responses. Because the compaction request is now always issued, that evidence should also decide whether reliance on the always-on default is justified, rather than synthetic success alone.
