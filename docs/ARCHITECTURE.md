# Direct subscription connection

How this provider talks to the Codex subscription backend, and the guarantees that come with it. [Initial scope](SCOPE.md) owns what the bridge does and does not do, [compaction design and limits](COMPACTION.md) owns the compaction contract, [the security requirements](../SECURITY.md) own the controls, and [the installation guide](INSTALL.md) owns prerequisites and procedures.

## Public surface

The provider registers as `codex-subscription` and accepts no configuration: any key fails with `CONFIG_INVALID`, and no token, endpoint or `.env` credential location is accepted. It declares `maxRetries: 0`, so a failed turn is reported rather than retried silently. Models come from the account's live catalog with each entry's disclosed context window and reasoning levels, and every model declares `inputModalities: ['text', 'image']`.

## Request flow

A turn projects offloaded images, validates the Harness input into Responses items under retained limits, resolves the selected model through the live catalog — cached in memory for 60 seconds, scoped by credential fingerprint and revalidated on each lookup and each turn — and takes the dedicated token. When the model discloses a usable context window and a proven replay window covers part of that history, the window replaces the prefix it covers, the plan is revalidated under the ordinary wire limits, and the request carries `context_management`; otherwise the bounded full history is sent. The request goes to `POST https://chatgpt.com/backend-api/codex/responses` with `store: false`, and the SSE response is validated incrementally: completed message and `function_call` items reconcile against streamed ones, and a published window is captured as replay metadata before the turn settles.

## Decision

The provider uses a direct subscription connection. A dedicated device-code OAuth login owns its own token lifecycle, and Codex credentials are never imported. [Initial scope](SCOPE.md) lists the features this covers.

The dedicated login implements OAuth, refresh, and store locking rather than requiring a Codex process for ordinary turns. Importing existing refresh tokens creates a shared rotation family, even when copies live in different files; dedicated login avoids that coupling.

## Transport

Only `https://auth.openai.com` OAuth/device endpoints and `https://chatgpt.com/backend-api/codex` model/Responses endpoints are used. Redirects are rejected. No custom host, raw token, proxy endpoint, arbitrary request override, shell, or Codex process is accepted in public configuration. The client identifies itself as `dsh-codex-subscription-bridge`, not the official CLI. Account/residency headers are derived from the OAuth token; JWT claims are routing and expiry hints, not signature-verification evidence.

Model catalog compatibility queries use `99.0.0` then `0.0.0` on an empty catalog. These are not claims about an installed CLI version. This provider does not supplement live catalogs with synthetic newer slugs, offline defaults, or large-context aliases. Each visible entry additionally projects the backend-disclosed `context_window` as the model's `contextWindow` when it is a positive safe integer; a malformed value fails closed and an absent value stays omitted, so host context accounting uses only the backend's own disclosure. Every entry also projects the backend-disclosed `supported_reasoning_levels` as the model's reasoning efforts, together with `default_reasoning_level` when it names one of them, so the host offers exactly the levels that model advertises. Malformed, oversized or duplicate disclosure is omitted rather than guessed, and the selected id is forwarded verbatim because the backend, not this bridge, owns the scale.

Text is converted to Responses input. System/developer instructions are separated, and `store` is false. Harness tool definitions are validated (names, sizes, JSON object parameters) and forwarded as `function` tools with `strict: false`; the bridge never executes tools. Assistant tool calls are forwarded as `function_call` items and tool results as `function_call_output` items keyed by `call_id`. Image blocks in user messages are read through the attachment service and sent as `input_image` base64 data URLs. Non-image file attachments never reach the bridge: the Harness runtime projects file blocks to text before every adapter dispatch, so the bridge has no file-attachment support and rejects any file block defensively. Reasoning blocks in replayed history are dropped, following the Harness host convention, and developer-role tool registry blocks are skipped defensively. SSE accepts bounded text, reasoning/lifecycle metadata, and completed `function_call` items; non-function execution items, refusals, malformed messages, failed/incomplete responses, and EOF without completion fail closed. Content-free notifications (`response.metadata`, `response.queued`) are listed explicitly and ignored, because failing a turn for one discards a usable answer. Any other unrecognized event still fails the turn, and its fixed error names the suspected cause, so a repeat is diagnosable without echoing upstream text. Completed message items also reconcile text when terminal output is null, without duplicating earlier completion events. A completed `function_call` item is reconciled idempotently against streamed tool calls: matching name and arguments replay is accepted, anything else fails with a fixed protocol error. Replay metadata is the one exception to failing closed: because the answer has already been delivered by the time a checkpoint is built, an unprovable compaction window is withheld and logged instead of failing the turn, and the streamed completed items — not the terminal array, which the live route trims — define the output order.

## Server-side compaction

Server-side compaction is always requested when the selected model discloses a usable context window. The request carries `context_management` with a threshold of `min(32768, floor(contextWindow / 2))`; the encrypted items the route returns are persisted as Harness replay metadata and substituted for the exact input prefix they cover, while ordinary text and tool events still go to the host. A window that cannot be proven is withheld and named in the host log instead of failing a turn whose answer was already delivered, and an explicit unsupported-parameter rejection retries once with the bounded full history. Harness local summaries and token accounting are unchanged by default; the opt-in preset that replaces them for this provider is described in [the installation guide](INSTALL.md#consolidate-on-server-side-compaction-opt-in). The client plugin marks the issuing turn in the chat from the assistant message's client-visible replay metadata. [The compaction contract](COMPACTION.md) owns the request shape, binding, wire bounds, refusal labels and remaining limits.

## Authentication lifecycle

The private dedicated directory is selected from launcher-inherited HOME, not project dotenv. Electron Desktop prefers launcher-owned DSH_HOME when set, which Desktop preserves across its login-shell environment merge. Auth helpers use the same Electron and DSH_HOME; no existing credential file is migrated. Credentials use a versioned ChatGPT-only schema. API keys are not accepted. Files are bounded to 64 KiB, opened without following symlinks, checked for ownership and permissions, and replaced atomically through private exclusive temporary files after fsync. The directory itself cannot be a symlink. Credential entries are checked before open, opened with `O_NOFOLLOW | O_NONBLOCK`, and checked again on the descriptor, so a FIFO cannot block before file-type validation.

A private directory lock serializes read-refresh-write, explicit login, and logout across processes. Waiters reread the store after acquiring the lock. Refresh begins within 120 seconds of token expiry and checks account continuity. Before dispatch, a durable `refresh_pending` state prevents replay after crashes, lost replies, malformed success responses, or persistence failures. Only a definite HTTP 429 rejection restores the prior grant for later retry. Successful persistence or explicit new login clears intent. Ambiguous outcomes require reauthentication instead of replaying the old refresh token. Terminal invalid-grant errors quarantine the local grant; rate limits do not destroy it. Raw upstream bodies never become errors. A crash after remote refresh but before durable local persistence can still require reauthentication; durable intent prevents automatic replay, but remote rotation cannot be made locally transactional.

Lock acquisition is bounded to 30 seconds. Login holds its lock while awaiting approval (at most 15 minutes); concurrent use may return `AUTH_BUSY`. Locks are not automatically stolen, because doing so can allow concurrent refresh. A crashed owner can leave `auth.lock`: stop all users of this store before manually removing that directory. A lock disappearing between an unsuccessful acquisition and its metadata check triggers another bounded acquisition attempt. Insecure locks remain rejected. No automatic lock-removal or token-export command exists.

The in-app panel reaches its endpoints through the Host's authenticated API carrier: the existing browser-session fence on Web and the trusted IPC carrier on Desktop. The initiating tab alone receives its one-time code; a random tab identifier may be kept in sessionStorage to recover ownership after reload, and no device code or tokens are stored there. Other tabs see only that a login is active.

## Bounds and remaining differences

Four concurrent owned operations (including cancellation cleanup), 30-second discovery deadline, 120-second turn deadline, 15-second JSON request timeout, 1 MiB JSON/event frames, 4 MiB aggregate SSE, 4096 SSE frames, 128 output text blocks, 1024 input messages with at most 64 blocks per non-tool message, and 256 KiB input/output text are enforced. Tool passthrough is bounded to 256 definitions, 256 KiB aggregate, 64-character names in `[A-Za-z0-9_-]`, 8 KiB descriptions, 64 KiB JSON object parameters, 256-byte `call_id` values, 2 MiB tool outputs, and 128 tool-update entries; oversize fails closed with fixed limit labels. Images are bounded to 4 MiB pixels, a 4096-pixel long edge, 1 MiB per encoded image, and 20 MiB aggregate base64 with a 10 MiB quantum; attachments are sanity-checked to 32 MiB. Oversized image requests fail with `IMAGE_OFFLOAD_REQUIRED` carrying an offload count so the Harness host can mark its oldest images offloaded and retry, and offloaded images are sent as text placeholders with zero visual tokens. JSON bodies and SSE framing use fixed buffers and yield to the event loop in bounded batches, so cancellation and deadline timers run. Pre-aborted requests are rejected before store preparation, and cancelled operations retain their admission slot until owned work and cleanup settle. Cancellation aborts transport readers even if a consumer pauses. Shutdown separately waits for owned authentication/HTTP cleanup and reader cancellation with a five-second bound; unresponsive cleanup reports TIMEOUT. OAuth body reads preserve caller cancellation and deadline classification across all auth paths. Successful catalog metadata is cached in memory for 60 seconds, scoped by credential fingerprint; credentials are checked again on each lookup and each turn. In-app login requests use four exact POST endpoints on Connection's authenticated carrier with the sole Typert Gateway interceptor preserved, 4 KiB body parsing, five-second request deadlines, no-store responses, admission bounded to four, and serialized account mutations.

The initial login path is device code only. Reasoning effort is validated to a bounded id and forwarded verbatim as Responses `reasoning.effort`, and the host offers exactly the levels the selected model's backend disclosure advertises. `temperature` is validated to a finite 0–2 number and forwarded; `maxTokens` is validated to a safe integer 1–1,000,000 and accepted as an advisory budget but deliberately not forwarded; `stop` sequences are rejected with fixed `UNSUPPORTED_OPTION` labeling. HTTP 429 responses are classified from a bounded error body: a recognized plan usage limit (`usage_limit_reached`, `usage_not_included`, or a dsh-llm quota match) becomes terminal `QUOTA`, optionally carrying a reset hint derived only from a validated `resets_at` integer (at most one week, clamped); any other body, an unusable body, or a non-usage code stays transient `RATE_LIMIT`. The hint is the only message part derived from upstream data, and upstream text is never copied into errors. Image acceptance on the subscription backend, per-model entitlement, and upstream acceptance of `temperature` on the subscription route are unverified.

Real-account evidence and its limits are recorded in [verification](VERIFICATION.md). Direct connection is not evidence of official third-party service support or absence of vulnerabilities.

## Safe diagnostics

Errors retain their existing fixed codes and append only allowlisted stage labels such as `[SSE_FRAME]`, `[SSE_EVENT_UNSUPPORTED]`, `[SSE_TERMINAL]`, or `[AUTH_REFRESH_UNCERTAIN]`. Unknown labels, upstream messages, event names, credentials and identifiers are never copied into diagnostics. Failure payloads are reconstructed from the allowlists even if an Error message was mutated. Empty string text deltas are valid no-op text updates; non-string and oversized deltas remain invalid.

## Transport dependencies

HTTP uses bundled Undici 7.29.1 and an explicit owned Agent, so the host's older fetch implementation and shared dispatcher are never used. Host dispatcher or proxy overrides are not inherited, and these fixed HTTPS destinations must be reachable directly. This does not patch Electron/Chromium or other host features.
