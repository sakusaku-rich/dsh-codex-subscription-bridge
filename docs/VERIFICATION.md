# Direct connection verification

## Reproducible checks

Use Node 22.23.3 on macOS and the committed lockfiles:

```sh
npm ci --ignore-scripts
npm ci --ignore-scripts --prefix verification/runtime
npm run verify
npm run test:install
npm run test:release-install
DSH_VERIFY_CLI="$PWD/verification/runtime/node_modules/@deepseek-ai/dsh/lib/bin.js" npm run test:profile
DSH_DESKTOP_EXECUTABLE="/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" npm run test:desktop
npm audit --audit-level=low
npm audit --audit-level=low --prefix verification/runtime
```

The `test:desktop` lane requires the pinned `verification/desktop` Electron package (or an explicit executable) and runs the root suite on the Desktop host. On the machine used for this record that lane fails inside `test/package.test.mjs`, which invokes `npm pack` as a child process; the same failure reproduces on the base commit before the release path was added, so it predates this work and is recorded rather than attributed to it. The Desktop release surface is covered independently by `test:release-install`, which drives the installed application's own resolver.

The root suite uses the small pinned Cordis/LLM peer dependency tree. The separate installation and profile checks require the full locked Harness 0.2.0-rc.2 runtime. All automated authentication and service fixtures are synthetic and disposable. Tests never import existing Codex credentials or send real model requests.

## Server-side compaction implementation (2026-10-16)

Compaction is requested on every turn whose selected model has a usable disclosed context window; the adapter has no configuration key, and any configuration fails with `CONFIG_INVALID`. `test/compaction.test.mjs` uses synthetic credentials, in-memory Responses fixtures, the pinned Harness runtime and its block assembler to cover encrypted window replay, tool continuation, persistence round trips, stale/changed state refusal, wire budgets, cancellation, missing output tails, covered images, the always-on request shape without configuration, the named refusal log, the `COMPACTION_UNAVAILABLE` boundary, and a one-time retry for explicit unsupported compaction parameters. `test/compaction-backend.test.mjs` pins the host `@deepseek-ai/dsh-compaction-basic` engine and covers the opt-in backend: only this provider is skipped, every other route is delegated, a missing route or session is tolerated, and each refusal label is produced. [The compaction research and limitations](COMPACTION.md) distinguish these checks from prior host-summary evidence. No real-account compaction request was made for this implementation.

On 2026-10-16, `npm run verify` passed on macOS with Node 22.23.3: syntax checks and all 111 tests, including 20 compaction-specific tests and the existing tarball installation/composition check. `git diff --check` also passed. Full Desktop/UI, real-service and long-running host-summary interaction were not exercised for this change, and the opt-in disable-and-insert profile composition was not mounted in a running Harness — only its module contract against the pinned host engine was checked.

## Model capability advertisement (2026-10-16)

The adapter declares each model's reasoning levels from the catalog's own `supported_reasoning_levels` disclosure, plus `default_reasoning_level` when it names a declared level; the host renders its effort selector only from that declaration. `test/text.test.mjs` covers the projection: disclosure order, description passthrough, the oversized-note drop, and omission for absent, oversized, duplicate, or malformed disclosure. `test/compaction.test.mjs` asserts through the pinned runtime that `resolveModelInfo` returns the disclosed ids and default, and `test/direct.test.mjs` asserts a disclosed id reaches the wire verbatim while an id the model does not disclose stays `INPUT_UNSUPPORTED`. Before this work no levels were declared at all, so the host offered no effort choice for this provider. A hardcoded two-level declaration was replaced after the live Codex catalog (`~/.codex/models_cache.json`, client version 0.162.0) showed six levels for the current models; the selector itself was not exercised in a browser session, and the subscription route's own catalog response was not observed directly.

On 2026-10-16, `npm run verify` passed on macOS with Node 22.23.3: syntax checks and all 112 tests. `git diff --check` also passed.

## Content-free stream notifications (2026-10-16)

A newly created Desktop session failed with `SSE_EVENT_UNSUPPORTED` after the subscription route had already streamed a complete answer on `gpt-6.1-sol`. A temporary diagnostic build (since removed) reported, for the offending event, a 17-character type with a `response.` prefix, four own fields, and no `delta`, `text`, `item` or `response` field; the type matched `response.metadata`. Because that event carries no response content, the turn was failed for a notification that could not affect the answer.

`response.metadata` and `response.queued` are now listed explicitly as ignored notifications, and `test/direct.test.mjs` asserts that a notification before or after the completed text still yields the `stop` finish with the full text, while an unlisted event still fails with `SSE_EVENT_UNSUPPORTED` plus the fixed cause hint. The diagnostic build, which reported only locally derived tokens and never an upstream string value, was validated against the existing no-upstream-text invariant before removal. The exact enumeration of all notifications the live route may send remains unverified; only `response.metadata` was directly observed.

On 2026-10-16, `npm run verify` passed on macOS with Node 22.23.3: syntax checks and all 113 tests. `git diff --check` also passed.

## Live server-side compaction (2026-10-16)

A long Desktop session on `gpt-6-luna` (13 turns, `reasoningEffort: low`) reached 33,915 input tokens, above the 32,768-token `compact_threshold`, and the subscription route returned a compaction item. The turn then failed with `PROTOCOL_INVALID [COMPACTION]`; a temporary closed-label diagnostic build identified the stage as `INDEX_MISSING`, meaning a streamed completed item had no counterpart in `response.completed.response.output`. The live route therefore trims that array, so the previous positional cross-check was unsound.

Two behaviors changed in response, both recorded in [the compaction contract](COMPACTION.md): the streamed completed items are now authoritative for the output order (a terminal compaction item that exists and disagrees still withholds the window), and an unprovable window is withheld and logged from a bridge-owned label vocabulary instead of failing a turn whose answer was already delivered. `test/compaction.test.mjs` covers the observed shape end to end — a streamed compaction item and message with a trimmed terminal array now publish a checkpoint that the next turn reuses — plus the labelled refusal path and the hard-failure cases that still reject.

This is the first evidence that the subscription route accepts `context_management` and issues encrypted compaction items. After the fix, the same session continued and confirmed the reuse half against the live service: the checkpoint was published on the turn priced at 38,612 input tokens (a compaction item plus one function call, 27,276 encrypted bytes), and the following three requests were priced at 11,787, 17,971 and 24,691 input tokens while the local transcript only grew. The drop is attributable to the checkpoint replacing its covered prefix — the route accepted the encrypted state it had issued. Checkpoint expiry, model switches, cancellation during compaction, quota impact and behaviour at the next threshold crossing remain unverified.

## Preset-owned compaction (2026-10-16)

The opt-in backend was mounted in a running Desktop profile and produced no observable change: `compaction-basic` was listed as present, `/compact` worked, and automatic condensation never fired for either a `codex-subscription` or an `openrouter` conversation even with `thresholdRatio` lowered to 0.002 and `retainRatio` to 0.0001, which put the threshold at 544 and 2,097 tokens against conversations priced at 5,000-40,000 input tokens.

Composing the same profile through the pinned CLI (`dsh --profile <copy> --dump-config`) explained it. Two facts came out of that dump:

- A plain `- id: …` patch entry is an *override* of an existing row, so the new row never loaded: the loader reported `patch: entry "codex-subscription-compaction" not found`. The bridge's own `cordis.patch.yml` already used the correct form, `- insert: [ … ]`; the opt-in snippet in the documentation did not.
- `@deepseek-ai/dsh-web-app` 0.2.0-rc.2 disables the top-level `compaction-basic` and `command-compact` rows — its patch explains that the token meter stays on the host plane while the backend "moves" — and declares the backend inside every agent preset (`preset-standard`, `preset-ptc`, `preset-minimal`, `preset-cordis` and the preset registry default) as a `compaction` group with `isolate: { compaction: true, toolResultPruner: true }`. A profile patch cannot address an entry nested in a preset's `plugins` list, so even a correctly inserted top-level row would provide a service no session consumes.

The opt-in entries were therefore removed from the owner's profile, which left the composition stock and warning-free; the observed absence of automatic condensation is the stock behavior, since each preset's `compaction-basic` keeps the default 0.8/0.16 ratios (~217,600 tokens for the 272,000-token Codex window). The duplicate condensation this opt-in targets is real: an earlier session on this profile raised 18 `compaction/prune` events on a `codex-subscription/gpt-6.1-sol` route.

The opt-in was then delivered the way the pinned Harness allows: `presets/codex-subscription.patch.yml` restates the shipped standard preset's 19 children with the `compaction` group's engine replaced, inserted **disabled** so installing the package adds no selectable preset. `scripts/sync-preset.mjs` derives it from `@deepseek-ai/dsh-web-app`'s own `presets/standard.patch.yml`, and the diff against that source is five lines (row id, `disabled: true`, preset id/name/description/order, engine). Two composition facts were then confirmed through `dsh --profile <copy> --dump-config`: a row inserted with `disabled: true` still resolves into the tree with all 19 children (so the Plugins page can list and enable it), and an id-keyed `disabled: false` override in the profile patch flips that same row to enabled, which is the write the Plugins page performs. `test/preset-artifact.test.mjs` pins the artifact's shape, composition, `!!js` conditions and generator rejections; `npm run preset:check` fails when the copy drifts from the pinned Harness and runs from the profile verification path.

The first application attempt after installing the artifact showed the row in the Plugins page as disabled with no usable switch. `dsh-client-ui-plugin-manager` locks a row's switch whenever the Host reports `readOnlyReason` or no live entry (`const locked = row.readOnlyReason !== void 0 || row.entryId === void 0`), and `setPluginEnabled` refuses the same rows, so a bundle-declared row that ships disabled cannot be enabled from that page: the enable step is the id-keyed profile-patch override, which the composition dump then showed as `disabled: false` with all 19 children and the bridge engine. The installation guide leads with that entry and records the locked switch, and the switch's own tooltip names the Host's reason, which distinguishes a general limit from a row-specific one.

The enabled preset was then exercised on the real account, with a threshold low enough to make both decisions observable. The installed verification copy — not the shipped artifact — carried `thresholdRatio: 0.002` / `retainRatio: 0.0001` in that preset's engine child, which puts the trigger at 544 tokens for the 272,000-token Codex window and 2,097 for a 1,048,576-token OpenRouter window. Session logs record the selected composition (`agentPreset: codex-subscription`), so the runs identify themselves:

- A 6,444-token session on `codex-subscription` raised **no** `compaction/*` event, although it was twelve times past its trigger: the preset-scoped engine received that route and declined.
- An 8,678-token session on `openrouter` under the same preset raised 18 `compaction/start`, 14 `compaction/summary`, 18 `compaction/end` and 7 `compaction/prune` events, which is the stock engine running through the delegation.
- `/compact` still condensed under the new preset, as it is inherited rather than overridden.

The count in the second run is an artifact of the test threshold: at ratio 0.002 the retained tail cannot fall below the trigger, so the stock engine retries within its bound, exactly as the earlier instrumented campaign recorded. It also multiplies auxiliary summarization — that run issued about fourteen summarize calls against OpenRouter — which is why the shipped artifact keeps the stock 0.8/0.16 ratios and the temporary value was reverted afterwards. The three post-mount checks in the installation guide are therefore observed, with automatic pressure as the only path that needed an artificial trigger to surface.

On 2026-10-16, `npm run verify` passed on macOS with Node 22.23.3: syntax checks and all 120 tests. `git diff --check` also passed.

## Model switching on a live checkpoint (2026-10-17)

The reuse binding was exercised across a real model switch. A session under the enabled preset read a 100 KB high-entropy sample, which pushed one request to 33,546 input tokens and made the route issue a compaction item on that same turn (checkpoint scope digest `4ae740a4…`, two items). The next two turns cost 6,772 and 6,788 input tokens, so that checkpoint was replacing its covered prefix.

The model was then switched from `gpt-5.6-terra` to `gpt-6-luna`. The next request cost 33,685 input tokens — the full local history — and the turn **succeeded**, and that same turn published a new checkpoint whose scope digest differs (`e742d569…`). The following turn cost 7,006 tokens, so reuse resumed under the new model. The two scope digests are the model binding that `compactionScope(account, model, tools, developer messages)` computes, observed on the wire: a switched model refuses the older window and re-issues one that matches.

An earlier attempt with a 190 KB sample of repetitive prose reached only 14,157 input tokens — about 11 bytes per token, so the artificial text never crossed the server's 32,768-token threshold — and therefore exercised nothing; the switch itself still worked. The high-entropy sample exists only to reach that threshold, and a real long conversation reaches it the same way.

## Covered controls

- Private dedicated OAuth storage: ownership, 0700/0600 modes, size/schema bounds, symlink and non-regular-file rejection, atomic durable replacement. FIFO tests demonstrate nonblocking refusal and lock release, including retry when a losing acquirer releases the lock after EEXIST but before its metadata check.
- Device login, logout, process-shared serialization, account continuity, grant quarantine and quota handling using synthetic HTTP responses and stores.
- Durable refresh intent prevents automatic replay after ambiguous remote outcomes, cancellation, persistence failure, and process restart. A definite HTTP 429 rejection allows retry; uncertain outcomes require a fresh login.
- Fixed HTTPS origins, redirect refusal, bounded JSON, safe fixed error codes and diagnostic labels, and cancellation after response headers.
- Live-catalog validation, hidden-model exclusion, compatibility fallback, auth-aware caching and fresh admission for each turn, and projection of the backend-disclosed `context_window` with fail-closed refusal of malformed window values.
- Bounded text history up to the 1024-message cap with validated tool definitions and executed tool-call history, user message images as `input_image` data URLs, offload-budget refusal with `IMAGE_OFFLOAD_REQUIRED`, rejection of other-role images, and `stop` rejection. `temperature` is validated to 0–2 and forwarded; `maxTokens` is validated and accepted as an advisory budget without forwarding. Synthetic 429 responses cover usage-limit bodies with and without `resets_at`, past and clamped resets, non-usage codes, oversized and unreadable bodies, and the bounded reset hint.
- Incremental bounded SSE framing, split UTF-8, CRLF/multiline data, empty text deltas, non-SSE MIME compatibility, completed-item and idempotent completed `function_call` reconciliation, and refusal of malformed, contradictory, non-function execution-bearing or incomplete responses.
- Four-operation admission including cancellation cleanup, pre-aborted refusal, paused-reader cancellation, event-loop yields, timeouts and bounded shutdown.
- The sign-in panel in a browser with synthetic OAuth responses: panel display, one-time code and fixed link, local diagnosis, cancellation, restarted login, automatic completion after simulated approval, confirmed local logout, and rejection of unknown fields and oversized payloads, with the settings API unchanged.
- Public adapter registration/disposal, actual npm tarball composition, MIT license inclusion, missing-auth errors, and synthetic CLI/SDK conversation.
- Fresh isolated Web-profile preparation, quoted paths, overwrite refusal and read-only doctor behavior for missing, insecure, locked and uncertain stores.
- The release install path against a locally built synthetic release: checksum parsing, fixed release-host URL construction, tag and asset-name refusal, a tampered bundle and an unlisted bundle refused with nothing created, a bundle whose packaged plugin is unlisted, an unreviewed transport, usage errors, and a full install whose manifest records the release identity with `workingTreeMayContainChanges` false.
- The release asset build itself: a tag that disagrees with `package.json`, an existing output directory, and development tooling appearing in the published package are all refused.
- The Desktop release surface on the installed application: the `desktop` profile name, the recorded host pair, no standalone runtime directory, no shadowing host peers, no launcher for the other surface, and no credential store after preparation; then the prepared profile registering the bridge when loaded through the application's own ASAR resolver, with an unauthenticated catalog read refused as `AUTH_REQUIRED`. This lane is skipped, not weakened, where the verified Desktop is absent, so CI does not claim it.
- The installed Desktop host pair: the packaged synthetic CLI/SDK conversation and shutdown on the Electron executable, and a disposable profile conversation driven through Desktop's ASAR resolver with actual host peers.

The source installer creates a new directory with an empty private HOME. It records the package integrity, commit, Node and Harness versions and disables installation scripts. The release installer verifies a downloaded artifact against its published SHA-256 before unpacking or running anything, records the release tag and verified digest instead of a commit, and fetches the pinned Harness runtime with lifecycle scripts disabled. A Desktop profile additionally records the verified host pair, deliberately contains no standalone runtime, and takes its host peers from the application tree. Verification does not modify a normal Harness profile.

The Desktop surface was checked by hand on the installed application at `5e9e301dd9dc8923b2762f76dacfc5751f6ca851` (Electron 44.0.0 / Node 24.18.1, Cordis 4.0.4 / LLM 0.2.0-rc.2): a profile prepared from a locally built release loaded through the application's ASAR resolver, provided `ctx.connection` and `ctx.webServer`, and registered `codex-subscription` alongside the host's own providers. An earlier iteration of this path omitted the web application bundle from the Desktop profile on the reasoning that the host supplies its own peers; the installed application then failed during host startup with `Cannot read properties of undefined (reading 'authenticatedUrl')` from `dsh-desktop-host`, because that host reads `ctx.connection` while booting. Owner-operated GUI launch caught this, and the synthetic verifier was extended to assert both services after the fact. The lesson is recorded here deliberately: asserting only provider registration did not prove the profile could boot.

Desktop preparation previously wrote an `auth.sh` helper, which never worked reliably: it loaded the plugin directly rather than through the application's profile boot, so `@deepseek-ai/dsh-llm` was resolved only by Node's ordinary directory walk. A profile that happened to sit under a tree also containing those peers made the helper appear to work, which briefly produced a wrong conclusion during this work: the same artifact succeeded under `artifacts/` in the checkout and failed under `TMPDIR`. The helper was removed rather than repaired, because sign-in, status and logout are provided by the settings panel and a Desktop profile has no command-line equivalent. The Web surface keeps its helper, which resolves against that profile's own runtime. No GUI was launched during automated checks: an Electron GUI cannot start in the sandboxed shell used for them, and a plain application launch failed there identically, so GUI startup remains owner-verified.

The release install tests build a synthetic release into a temporary directory with the real release build script and drive the real `install.sh` against it over a `file://` transport. They never contact GitHub or the real repository, and the plugin package never comes from the npm registry.

That synthetic-only coverage hid a real defect. The downloader refused every redirect, following the fixed-origin rule used by the provider transport, but GitHub serves a release asset with one 302 to `release-assets.githubusercontent.com`. The first tagged release therefore could not be installed at all, and nothing in the suite noticed, because the `file://` transport never redirects. The downloader now follows redirects hop by hop under a fixed two-host allowlist instead, and `test/integration/release-download.test.mjs` covers it: refusals are exercised against a local origin with a redirect table, and the accepting case downloads a published asset from the real release. The accepting case skips rather than fails when the network is unavailable, so the offline suite stays meaningful.

The lesson is recorded deliberately: a transport that is only ever exercised through `file://` does not test the transport. Any claim about the `https://` path requires a real download, not an argument that the code is equivalent.

Real release-asset reachability is now verified: the `v0.0.1` assets were downloaded unauthenticated after the repository became public, both digests matched the published `SHA256SUMS`, and profiles were prepared from those downloads for the Web and Desktop surfaces.

The `v0.0.2` release added the existing-profile mode, and that path was exercised by the owner against their own Desktop profile over `https`, from the published `install.sh` with no local source override. The bridge reached a working state: sign-in succeeded and a model produced a real response. The install left the profile's other plugin (`dsh-theme-studio`) and its `cordis.patch.yml` provider configuration intact, and the backup directory reproduced the profile's original `package.json` hash exactly, so the run was reversible. No credentials, device codes, token values or response content are recorded here.

Two operational problems surfaced while preparing that run, both in the preparation rather than the installer. The published `install.sh` needs both the installer bundle and the plugin package present in the download source, and fetching only the plugin package fails with `ENOENT` for the bundle; and the `--profile` mode does not exist in the `v0.0.1` bundle, so it requires `v0.0.2` or later. Both are noted in the installation guide rather than left to be rediscovered.

## Real-account evidence and limits

The owner confirmed dedicated device login and model selection. Two separately authorized short diagnostic requests confirmed an authenticated catalog including `gpt-6.1-sol` and an HTTP 200 response with a 6992-byte SSE-framed body under a non-SSE MIME header. No credentials, account IDs, prompt text or response text were printed or saved. The exact media type was not retained.

The owner separately authorized one further diagnostic session on a low-cost model. The authenticated catalog listed seven visible models and disclosed per-model context metadata (`context_window`, `max_context_window`, `auto_compact_token_limit`, `truncation_policy`); `gpt-6-luna` reported a 272000-token combined window with `auto_compact_token_limit: null`, so host-side compaction pressure depends on the bridge projecting the disclosed window rather than any server-side limit. One short generation turn through the adapter on that model finished with `stop` and mapped usage of 16 input, 7 output and 23 total tokens; only reply byte counts were recorded. This evidence came from a temporary diagnostic script, not the prepared smoke command.

The owner then authorized a bounded compaction campaign on the same low-cost model to prove that the projected window activates host automatic compaction. A disposable Harness profile (uncommitted scratch area, bridge installed from the built tarball) ran multi-turn headless sessions on the real account against a 57,800-byte workspace file read through the host `read` tool. The session `request/context` event carried `contextWindow: 272000` — sourced through the adapter's `resolveModel` `context: { contextWindow }`, which is the exact route `compaction-basic` reaches via `ctx.llm.resolveModelInfo`. To make the trigger's otherwise silent decision points observable, the disposable verification runtime's copy of `@deepseek-ai/dsh-compaction-basic` was temporarily extended with stderr diagnostics gated on `DSH_CMP_DEBUG`; that instrumentation lives only in the throwaway runtime and is not shipped. With it, one run showed the complete chain: the `agent/pre-step` hook dispatched with a real agent, `routedTarget` resolved `codex-subscription`/`gpt-6-luna` from the bridge-routed header config, the patched target policy row applied, `resolveModelInfo` returned the 272000-token window, the spec was computed, ranges were selected, and `compactRegion` completed — the session log durably records six `compaction/start` / `compaction/summary` / `compaction/end` cycles whose summaries were produced by the auxiliary summarize call through the bridge on the real account.

The deliberate test threshold (ratio 0.001, i.e. 272 tokens) is smaller than the assembled system head alone (~669 tokens), so no compaction can bring the measured total below it; `compaction-basic` then throws `compaction still above threshold after N compaction attempts`, which the automatic handler warns about and continues from, invisibly in the headless runtime. That throw is an artifact of the test threshold, not of the bridge; the earlier "no compaction at all" reading of the uninstrumented runs was wrong — compaction was firing throughout. Spend is recorded deliberately because it exceeded the initial estimate: the campaign's main steps used 31,277 recorded tokens in the final run (4,361 + 4,627 + 15,979 + 6,310), its six auxiliary summarize calls are not recorded in session usage and are estimated at roughly 15,000–30,000 tokens, and cumulative `gpt-6-luna` usage across all runs of the campaign is roughly 130,000–150,000 tokens against an original ~20,000-token estimate. Each pre-step can issue up to two summarize calls before the retry bound, so unrealistic thresholds multiply auxiliary spend; a realistic ratio avoids this.

Still unverified for compaction: a below-threshold successful return observed in a paid run at a realistic ratio (with a visibly reduced subsequent step input), the runtime sink for `ctx.logger` warnings in headless mode, and behavior at the default 0.8/0.02 ratios, which is reasoned from code rather than observed.

Real multi-turn generation through the adapter, real refresh and revocation, interruption recovery, entitlement to models beyond those confirmed, latency and a complete Web conversation remain unverified. Real tool-call and image turns, upstream acceptance of forwarded `temperature`, `input_image` acceptance, `strict: false` requirements, vision-token accounting, reasoning efforts beyond `low`/`high`, and the presence of `resets_at` or `plan_type` in real 429 bodies remain unverified. Full real GUI, login, refresh and revocation behavior on the installed Desktop runtime remains owner-operated verification. Each further account operation requires separate explicit authorization. The prepared real-account smoke command is not part of CI and has not been run for this transport; authorized real-account E2E verification remains a release preparation task.

## Continuous integration

[CI](../.github/workflows/ci.yml) runs on pushes to the default branch, manual dispatch and pull requests that are not drafts; marking a draft ready for review starts its first run. CI uses `macos-15` and `.node-version`. Official checkout v7.0.1 and setup-node v7.1.0 are pinned to commit SHAs. Token access is read-only, checkout credentials are not persisted, and no cache or repository secrets are configured. The job has a 20-minute deadline, disables install scripts, audits both locked trees, runs all reproducible checks above, and requires tracked files to remain unchanged. It does not publish packages or perform account operations.

CI adds a locked Electron 44.0.0 test package and an explicit checksum-verifying binary download before synthetic host checks; it does not install Harness Desktop or run real login. The installed-ASAR composition lane is verified locally rather than claimed as a CI check. The packaged tarball excludes `.github`, so the workflow link above resolves only inside a full checkout. Audit results only cover known advisories; no finite audit or test suite establishes absence of unknown vulnerabilities.

The release install lane runs in CI against a locally published synthetic release over a `file://` transport. It does not download a real release asset, and CI does not publish packages, tag releases, or perform account operations. Creating the first real release asset is a separate decision.
