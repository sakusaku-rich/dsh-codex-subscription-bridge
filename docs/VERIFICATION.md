# Direct connection verification

This record separates what holds now from how each step was verified. The current state lists the commands, the controls they cover, and what is confirmed or still open; the dated entries after it keep the evidence in the order it was gathered.

## Reproducible checks

Use Node 22.23.3 on macOS and the committed lockfiles:

```sh
npm ci --ignore-scripts
npm ci --ignore-scripts --prefix verification/runtime
npm run verify
npm run test:install
npm run test:auth-ui
npm run test:profile-install
npm run test:release-install
DSH_VERIFY_CLI="$PWD/verification/runtime/node_modules/@deepseek-ai/dsh/lib/bin.js" npm run test:profile
DSH_DESKTOP_EXECUTABLE="/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" npm run test:desktop
npm audit --audit-level=low
npm audit --audit-level=low --prefix verification/runtime
```

`npm run test:profile` also runs `npm run preset:check`, so preset drift fails that lane. Which check isolates what:

| Symptom | Check |
| --- | --- |
| A window refusal or `COMPACTION_UNAVAILABLE` | `node --test test/compaction.test.mjs` |
| `preset:check` drift | `npm run preset:sync`, then review the diff |
| A profile or packaged CLI/SDK composition failure | `npm run test:profile` (needs the pinned runtime) |
| A release asset, checksum or download failure | `npm run test:release-install` |
| A settings-panel or Connection-carrier failure | `npm run test:auth-ui` |
| A Desktop host-pair or ASAR-resolver failure | `npm run test:desktop` with `DSH_DESKTOP_EXECUTABLE` set |
| An adapter protocol or transport failure | `npm run verify` (root suite) |

The `test:profile`, `test:auth-ui` and `test:desktop` rows need the pinned runtimes installed by the commands above: the first two use `verification/runtime`, and without it they fail to resolve `@deepseek-ai/dsh` rather than reporting a real defect. The `test:desktop` lane requires the pinned `verification/desktop` Electron package (or an explicit executable) and runs the root suite on the Desktop host. On the machine used for this record that lane failed inside `test/package.test.mjs`, which invokes `npm pack` as a child process, on both the base commit and this one; it is recorded rather than attributed to this work. That is a machine-specific observation at the time of writing, not the lane's current state: the run recorded under [runtime and platform evidence](#runtime-and-platform-evidence) passed on the installed application at `cacd297`. The Desktop release surface is covered independently by `test:release-install`, which drives the installed application's own resolver.

The root suite uses the small pinned Cordis/LLM peer dependency tree. The separate installation and profile checks require the full locked Harness 0.2.1-rc.2 runtime. All automated authentication and service fixtures are synthetic and disposable. Tests never import existing Codex credentials or send real model requests.

## Covered controls

- Private dedicated OAuth storage: ownership, 0700/0600 modes, size/schema bounds, symlink and non-regular-file rejection, atomic durable replacement. FIFO tests demonstrate nonblocking refusal and lock release, including retry when a losing acquirer releases the lock after EEXIST but before its metadata check.
- Device login, logout, process-shared serialization, account continuity, grant quarantine and quota handling using synthetic HTTP responses and stores.
- Durable refresh intent prevents automatic replay after ambiguous remote outcomes, cancellation, persistence failure, and process restart. A definite HTTP 429 rejection allows retry; uncertain outcomes require a fresh login.
- Fixed HTTPS origins, redirect refusal, bounded JSON, safe fixed error codes and diagnostic labels, and cancellation after response headers.
- Live-catalog validation, hidden-model exclusion, compatibility fallback, auth-aware caching and fresh admission for each turn, and projection of the backend-disclosed `context_window` with fail-closed refusal of malformed window values.
- Bounded text history up to the 1024-message cap with validated tool definitions and executed tool-call history, user message images as `input_image` data URLs, offload-budget refusal with `IMAGE_OFFLOAD_REQUIRED`, rejection of other-role images, and `stop` rejection. `temperature` is validated to 0–2 and forwarded; `maxTokens` is validated and accepted as an advisory budget without forwarding. Synthetic 429 responses cover usage-limit bodies with and without `resets_at`, past and clamped resets, non-usage codes, oversized and unreadable bodies, and the bounded reset hint.
- Incremental bounded SSE framing, split UTF-8, CRLF/multiline data, empty text deltas, non-SSE MIME compatibility, completed-item and idempotent completed `function_call` reconciliation, and refusal of malformed, contradictory, non-function execution-bearing or incomplete responses. Per-stream framing limits derived from the compaction window: a frame admitted up to twice the checkpoint bound, the aggregate stream up to the item's three occurrences plus the fixed frame defaults, the event count derived from the same admitted window (default 4096, cap 65536), and invalid or below-floor limit values rejected as plain errors before the stream starts. Events outside the consumed set are ignored, and a test asserts an unknown event carrying content-shaped fields projects no text, tool call or usage.
- Four-operation admission including cancellation cleanup, pre-aborted refusal, paused-reader cancellation, event-loop yields, timeouts and bounded shutdown.
- The sign-in panel in a browser with synthetic OAuth responses: panel display, one-time code and fixed link, local diagnosis, cancellation, restarted login, automatic completion after simulated approval, confirmed local logout, and rejection of unknown fields and oversized payloads, with the settings API unchanged.
- Public adapter registration/disposal, actual npm tarball composition, MIT license inclusion, missing-auth errors, and synthetic CLI/SDK conversation.
- Fresh isolated Web-profile preparation, quoted paths, overwrite refusal and read-only doctor behavior for missing, insecure, locked and uncertain stores.
- The release install path against a locally built synthetic release: checksum parsing, fixed release-host URL construction, tag and asset-name refusal, a tampered bundle and an unlisted bundle refused with nothing created, a bundle whose packaged plugin is unlisted, an unreviewed transport, usage errors, and a full install whose manifest records the release identity with `workingTreeMayContainChanges` false.
- The release asset build itself: a tag that disagrees with `package.json`, an existing output directory, and development tooling appearing in the published package are all refused.
- The Desktop release surface on the installed application: the `desktop` profile name, the recorded host pair, no standalone runtime directory, no shadowing host peers, no launcher for the other surface, and no credential store after preparation; then the prepared profile registering the bridge when loaded through the application's own ASAR resolver, with an unauthenticated catalog read refused as `AUTH_REQUIRED`. This lane is skipped, not weakened, where the verified Desktop is absent, so CI does not claim it.

Run at `cacd297` on the installed application: the runtime pair matched Electron 44.0.0 / Node 24.18.1, the root suite passed under the host runtime, and the packaged profile lane reported `realAccount: not tested`. The prepared verification profile for that commit is a new directory; nothing was launched and no login was performed. ## Continuous integration

[CI](../.github/workflows/ci.yml) runs on pushes to the default branch, manual dispatch and pull requests that are not drafts; marking a draft ready for review starts its first run. CI uses `macos-15` and `.node-version`. Official checkout v7.0.1 and setup-node v7.1.0 are pinned to commit SHAs. Token access is read-only, checkout credentials are not persisted, and no cache or repository secrets are configured. The job has a 20-minute deadline, disables install scripts, audits both locked trees, runs the checks above except the installed-ASAR desktop lane and `npm run test:profile-install`, which are local-only, and requires tracked files to remain unchanged. It does not publish packages or perform account operations.

CI adds a locked Electron 44.7.0 test package and an explicit checksum-verifying binary download before synthetic host checks; it does not install Harness Desktop or run real login. The installed-ASAR composition lane is verified locally rather than claimed as a CI check. The packaged tarball excludes `.github`, so the workflow link above resolves only inside a full checkout. Audit results only cover known advisories; no finite audit or test suite establishes absence of unknown vulnerabilities.

The release install lane runs in CI against a locally published synthetic release over a `file://` transport. It does not publish or tag a release, and CI performs no account operations; the download lane makes one unauthenticated fetch of the published `v0.0.1` `SHA256SUMS` when the network is available and skips otherwise. Real releases are prepared and published outside CI.

### Notification events fail turns (2026-10-17)

A turn failed with `PROTOCOL_INVALID [SSE_EVENT_UNSUPPORTED]` after the backend had already streamed a complete answer. The message said the response content was unaffected, and that was accurate: the failure discarded usable content rather than detecting corruption. This is the third occurrence of the same class, after `response.metadata` and the annotation/item-progress report below.

**First attempt, and why it was insufficient.** The two-name notification list was widened to two reviewed groups — backend-state names, and the progress/part events of unprojected item families, plus annotations on projected text — with regression tests. The owner installed that build into their Desktop profile, and the same error recurred on the next real turn. The approach was wrong in kind, not merely incomplete: it assumed the bridge could enumerate a live third-party stream's notification vocabulary, and each enumeration was falsified by the next event.

**What settled it.** The verified Harness bundles a reference Responses client, `@earendil-works/pi-ai` (`api/openai-responses-shared.js`), extracted read-only from the installed application's `app.asar`. Its dispatch handles `response.created`, `response.output_item.added`/`.done`, `response.reasoning_summary_text.delta`, `response.reasoning_summary_part.done`, `response.reasoning_text.delta`, `response.output_text.delta`, `response.refusal.delta`, `response.function_call_arguments.delta`/`.done`, `response.custom_tool_call_input.delta`/`.done`, `response.completed`, `response.incomplete` and `response.failed` — and has **no** catch-all that fails an unknown event. Only `error` and `response.failed` throw, plus a missing-terminal check. The bridge's allowlist was therefore stricter than the host it feeds, and that strictness was the defect.

**The change.** The consumed set is now closed and explicit (`response.output_text.delta`/`.done`, `response.output_item.added`/`.done`, `response.completed`), terminal failures and refusals stay fatal, and every other event is ignored. Every consumed event keeps its existing strict validation, so only those branches can project text, tool calls or usage. A new test asserts an unknown event carrying content-shaped fields (`delta`, `text`, a `function_call` item, `response.usage`) contributes no text, no tool call and no usage, which is what preserves the fail-closed property that matters: content cannot be injected through an unhandled event. The now-unreachable `SSE_EVENT_UNSUPPORTED` label and the closed cause-hint list that existed only for it were removed.

**Evidence on the real Desktop host.** Both builds were installed into separate disposable profiles under `/private/tmp` with a throwaway `DSH_HOME`, booted through the installed application's own ASAR resolver on the pinned Electron 44.0.0 / Node 24.18.1 host, and driven with synthetic credentials and in-memory SSE fixtures — no real model calls, and the owner's credential store untouched. The same harness produced opposite results:

| Event injected mid-stream | Released v0.0.3 | This change |
| --- | --- | --- |
| `response.output_text.annotation.added` | failed the turn | `stop`, text delivered |
| `response.web_search_call.in_progress` | failed the turn | `stop`, text delivered |
| `response.code_interpreter_call.in_progress` | failed the turn | `stop`, text delivered |
| `response.code_interpreter_call_code.delta` | failed the turn | `stop`, text delivered |
| `response.metadata` (control) | `stop` | `stop` |
| unknown event, fail-closed check | rejected | rejected |

On the released build the failing cases reported `finish: error` while the text `"Hello"` had already been delivered, which is the reported symptom reproduced under test.

**What remains unverified.** No raw live event name was captured for this report, so which specific event triggered it is not known; the change is deliberately independent of that, since no enumeration is needed. The live backend's full event vocabulary is likewise unverified and is no longer claimed.

**Live confirmation.** The owner installed this build into their Desktop profile, restarted the application, and confirmed that Codex-model conversations complete normally. This is the step that the first attempt failed: that build was installed the same way and the error recurred on the next real turn. The specific event that used to trigger the failure is still unidentified, and identifying it is no longer meaningful, because the fix does not depend on the backend's notification vocabulary.

On 2026-10-17, `npm run verify` passed on macOS with Node 22.23.3: syntax checks and all 125 tests. `git diff --check` also passed.

### Real-account diagnostics and campaign (2026-10-16)

The owner confirmed dedicated device login and model selection. Two separately authorized short diagnostic requests confirmed an authenticated catalog including `gpt-6.1-sol` and an HTTP 200 response with a 6992-byte SSE-framed body under a non-SSE MIME header. No credentials, account IDs, prompt text or response text were printed or saved. The exact media type was not retained.

The owner separately authorized one further diagnostic session on a low-cost model. The authenticated catalog listed seven visible models and disclosed per-model context metadata (`context_window`, `max_context_window`, `auto_compact_token_limit`, `truncation_policy`); `gpt-6-luna` reported a 272000-token combined window with `auto_compact_token_limit: null`, so host-side compaction pressure depends on the bridge projecting the disclosed window rather than any server-side limit. One short generation turn through the adapter on that model finished with `stop` and mapped usage of 16 input, 7 output and 23 total tokens; only reply byte counts were recorded. This evidence came from a temporary diagnostic script, not the prepared smoke command.

The owner then authorized a bounded compaction campaign on the same low-cost model to prove that the projected window activates host automatic compaction. A disposable Harness profile (uncommitted scratch area, bridge installed from the built tarball) ran multi-turn headless sessions on the real account against a 57,800-byte workspace file read through the host `read` tool. The session `request/context` event carried `contextWindow: 272000` — sourced through the adapter's `resolveModel` `context: { contextWindow }`, which is the exact call path `compaction-basic` reaches via `ctx.llm.resolveModelInfo`. To make the trigger's otherwise silent decision points observable, the disposable verification runtime's copy of `@deepseek-ai/dsh-compaction-basic` was temporarily extended with stderr diagnostics gated on `DSH_CMP_DEBUG`; that instrumentation lives only in the throwaway runtime and is not shipped. With it, one run showed the complete chain: the `agent/pre-step` hook dispatched with a real agent, `routedTarget` resolved `codex-subscription`/`gpt-6-luna` from the header config routed through the bridge, the patched target policy row applied, `resolveModelInfo` returned the 272000-token window, the spec was computed, ranges were selected, and `compactRegion` completed — the session log durably records six `compaction/start` / `compaction/summary` / `compaction/end` cycles whose summaries were produced by the auxiliary summarize call through the bridge on the real account.

The deliberate test threshold (ratio 0.001, i.e. 272 tokens) is smaller than the assembled system head alone (~669 tokens), so no compaction can bring the measured total below it; `compaction-basic` then throws `compaction still above threshold after N compaction attempts`, which the automatic handler warns about and continues from, invisibly in the headless runtime. That throw is an artifact of the test threshold, not of the bridge; the earlier "no compaction at all" reading of the uninstrumented runs was wrong — compaction was firing throughout. Spend is recorded deliberately because it exceeded the initial estimate: the campaign's main steps used 31,277 recorded tokens in the final run (4,361 + 4,627 + 15,979 + 6,310), its six auxiliary summarize calls are not recorded in session usage and are estimated at roughly 15,000–30,000 tokens, and cumulative `gpt-6-luna` usage across all runs of the campaign is roughly 130,000–150,000 tokens against an original ~20,000-token estimate. Each pre-step can issue up to two summarize calls before the retry bound, so unrealistic thresholds multiply auxiliary spend; a realistic ratio avoids this.

### Live server-side compaction (2026-10-16)

A long Desktop session on `gpt-6-luna` (13 turns, `reasoningEffort: low`) reached 33,915 input tokens, above the then-shipped 32,768-token `compact_threshold`, and the subscription backend returned a compaction item. The turn then failed with `PROTOCOL_INVALID [COMPACTION]`; a temporary closed-label diagnostic build identified the stage as `INDEX_MISSING`, meaning a streamed completed item had no counterpart in `response.completed.response.output`. The live backend therefore trims that array, so the previous positional cross-check was unsound.

Two behaviors changed in response, both recorded in [the compaction contract](COMPACTION.md): the streamed completed items are now authoritative for the output order (a terminal compaction item that exists and disagrees still withholds the window), and an unprovable window is withheld and logged from a bridge-owned label vocabulary instead of failing a turn whose answer was already delivered. `test/compaction.test.mjs` covers the observed shape end to end — a streamed compaction item and message with a trimmed terminal array now publish a checkpoint that the next turn reuses — plus the labelled refusal path and the hard-failure cases that still reject.

This is the first evidence that the subscription backend accepts `context_management` and issues encrypted compaction items. After the fix, the same session continued and confirmed the reuse half against the live service: the checkpoint was published on the turn priced at 38,612 input tokens (a compaction item plus one function call, 27,276 encrypted bytes), and the following three requests were priced at 11,787, 17,971 and 24,691 input tokens while the local transcript only grew. The drop is attributable to the checkpoint replacing its covered prefix — the backend accepted the encrypted state it had issued. Checkpoint expiry, cancellation during compaction, quota impact and behaviour at the next threshold crossing remain unverified; model switching was verified later and is recorded below.

### Preset-owned compaction (2026-10-16)

The opt-in backend was mounted in a running Desktop profile and produced no observable change: `compaction-basic` was listed as present, `/compact` worked, and automatic condensation never fired for either a `codex-subscription` or an `openrouter` conversation even with `thresholdRatio` lowered to 0.002 and `retainRatio` to 0.0001, which put the threshold at 544 and 2,097 tokens against conversations priced at 5,000-40,000 input tokens.

Composing the same profile through the pinned CLI (`dsh --profile <copy> --dump-config`) explained it. Two facts came out of that dump:

- A plain `- id: …` patch entry is an *override* of an existing row, so the new row never loaded: the loader reported `patch: entry "codex-subscription-compaction" not found`. The bridge's own `cordis.patch.yml` already used the correct form, `- insert: [ … ]`; the opt-in snippet in the documentation did not.
- `@deepseek-ai/dsh-web-app` 0.2.0-rc.2 disables the top-level `compaction-basic` and `command-compact` rows — its patch explains that the token meter stays on the host plane while the backend "moves" — and declares the backend inside its standard, ptc and cordis agent presets (`preset-minimal` has none), each as a `compaction` group with `isolate: { compaction: true, toolResultPruner: true }`; the preset registry default resolves to `standard`. A profile patch cannot address an entry nested in a preset's `plugins` list, so even a correctly inserted top-level row would provide a service no session consumes.

### Window bound derived from the same measurement, and oldest-item recovery (2026-10-18)

The checkpoint byte cap was a fixed 512 KiB while the threshold became window-derived, so the two no longer shared a measurement: a window the backend could produce was larger than the cap the bridge would accept, and the refusal meant the full history was resent and the next turn crossed the threshold again. The cap is now derived from the same window as the threshold, with 512 KiB kept as the floor when no window is disclosed. Recovery follows the official client, which removes the oldest history item when the window is exceeded while compacting rather than failing the turn: a window past its bound drops the oldest covered items and names the count in the host log. A persisted window is never trimmed, because trimming would change the digest it was proved against, so a stored window past the bound is refused whole; the same oldest-end recovery applies to the full-history fallback. The refusal names its own stage instead of reporting the generic label.

Synthetic tests cover the derived bound, the capture-time drop, the persisted-window case, the refusal when nothing is left to drop, and the stage-preserving refusal label.

Measured on a real account (dedicated login, gpt-6-luna, window 272,000, threshold 258,400, derived bound 2,359,296 bytes): the backend accepts a request whose measured count is past the model window and compacts it. An untrimmed transcript of 1,647,826 bytes was measured by the backend as 320,901 input tokens — 18% past the window — and returned HTTP 200 with a checkpoint published. A transcript of 2,659,060 bytes was trimmed by the bridge from the oldest end (5 items) to 1,961,565 bytes, measured by the backend as 381,828 input tokens — 40% past the window — and also returned HTTP 200 with a checkpoint published. No rejection occurred in either case.

So the derived bound is a resource limit for one request, not a guard against rejection, and trimming enforces that limit rather than keeping the request inside the model window. Trimming deletes what it drops; a dropped item carries no summary, which is the difference from compaction. The claim that a window cannot exceed the cap still rests on the measured reduction ratio (about 25% on the observed crossing turn) plus the input bound, not on an observed oversized window. The count named in the log is a count of dropped items, not a token count. What is still not observed: the shape of the view the backend passed to the model on a past-window turn — summary or truncation — cannot be read from the checkpoint item count, and the same payload with trimming disabled has not been compared.

### Stateful conversation chain — attempted and rejected by the backend (2026-10-18)

The request shape moved to `store: true` with `previous_response_id`, the form the official client uses, because a stateless turn has to resend the compacted prefix and so cannot hit a cached prefix on a compaction turn. Measured on a dedicated login against `POST https://chatgpt.com/backend-api/codex/responses` with model gpt-6-luna, that shape is rejected:

- `store: true` → HTTP 400. The message matches the fixed words `store`, `must`, `false` (26 characters). The same body with `store: false` returned 200 on the same model.
- `previous_response_id` → HTTP 400 with `store: false`. The message matches `previous_response_id` and `unsupported` (43 characters).
- The backend's error body is `{ detail }`, not the `{ error: { code, param } }` shape the retry path reads, so the parameter-rejection retry never fired and the turn ended as `UPSTREAM_FAILED`.
- The live catalog discloses no `effective_context_window_percent` for gpt-6-luna; the response carries `context_window` only, so the shipped fallback is what runs.

The implementation is therefore back to the stateless form: `store: false`, no `previous_response_id`, and the compaction window replayed in the input array. The only capability statefulness would have provided — a prefix that survives compaction — cannot be obtained on this backend, and the cache hit on a firing turn stays at 0%. Whether the rejection is endpoint-wide or this account's storage policy is not established; the message wording is a requirement, not a preference, and the official client's guidance line treats `store: false` or ZDR as a separate case in which content must be replayed.

Two differences were closed; the rest are recorded as differences deliberately not closed in [the compaction contract](COMPACTION.md#differences-deliberately-not-closed).

**Per-model effective percent.** The shipped 0.95 was the value observed on this account, not a per-model measurement, so a model disclosing a different percent would have been measured wrong. **Oldest-end recovery on the full-history fallback.** The official client removes the oldest history item when the window is exceeded while compacting instead of failing the turn. The bridge now drops the oldest items until the request fits, keeps a tool call and its executed result as one unit so no result is left orphaned, and never drops an image occurrence — the host owns the attachment store and offloads its oldest images instead. Nothing left to drop is still a refusal, and limits are never raised silently.

The cost recorded here belongs to the stateful chain the backend rejected, not to the shape this implementation uses. Under the stateless form a trimmed turn still publishes replay metadata, because the bridge proves the input it sent, and the next turn validates that window again; trimming does not start a new conversation.

**What the binary can show about the official client.** The string `context_management` does not appear anywhere in the shipped binary, so the official client never sends the inline shape the bridge uses; its compaction goes through the standalone `responses/compact` path. Its compaction item is `SerializedCompactedItem` with six fields — `message`, `replacement_history`, `window_number`, `first_window_id`, `previous_window_id`, `window_id` — and the binary carries doc comments for the chain: `window_number` is the "Monotonic position of this context window within the thread", `first_window_id` the "UUIDv7 identity of the first context window in this thread's window chain", `previous_window_id` the "UUIDv7 identity of the context window immediately before this one", `window_id` the "UUIDv7 identity of this context window". The item the inline backend returns has three fields — `encrypted_content`, `id`, `type` — and carries no readable `message`, which is why the bridge can only echo it. The client's own comment says to "treat compacted items as opaque state".

The client's compaction trigger reasons appear in the binary as the names `user_requested`, `context_limit`, `model_downshift` and `comp_hash_changed`. These are reason names; the condition attached to each is not readable from the binary. If they are triggers, auto compaction is not only a threshold crossing — it would also fire on a model downshift and on a change to the compaction configuration, and the bridge has no equivalent for those two, because it holds no compaction configuration to hash and sends one threshold per request. Not readable from the binary: whether the client removes the oldest history item once or repeats, and what it uses when `auto_compact_token_limit` is null.

Not verified: no real-account request has carried a catalog-disclosed percent. A real-account request has been trimmed from the oldest end, recorded under [the window bound entry](#window-bound-derived-from-the-same-measurement-and-oldest-item-recovery-2026-10-18); what remains unverified is a real turn that trims while carrying a disclosed percent.

### SSE framing versus the compaction window (2026-10-18)

A real subscription turn failed with `[SSE_FRAME] LIMIT_EXCEEDED` after the window-derived bounds shipped. The request bound admits one compaction item at the threshold in bytes — a 872,000-token window admits about 6.3 MiB of `encrypted_content` at the conservative 8 bytes per token — while the SSE frame parser still refused any single event payload above its fixed 1 MiB default. An item between those bounds killed the stream before the capture could refuse it gently, and because the stream died before `response.completed`, no window was published and the next turn resent the full history, so the failure repeated every turn on a long thread. The presence of the frame label without a preceding `checkpoint was not published` warning is what located the death mid-stream.

The fix raises the framing limits per stream when a threshold is derived, instead of widening the fixed defaults: one event frame may carry twice the checkpoint bound, and the aggregate stream bound admits the item's three occurrences (`response.output_item.added`, `.done`, and the `response.completed` echo) plus the fixed frame defaults as margin. The event count rises with the same admitted window — the count sizes from the frame bound at a conservative 128-byte event envelope estimate, capped at 65536, so a stream of many small deltas, including reasoning deltas the bridge does not forward, is bounded by the same admitted window and not by a fixed count the framing limits cannot move; smaller events are bounded by the aggregate byte limit. An item past the capture bound but inside the raised frame limit now hits the gentle refusal — the checkpoint is withheld with its logged label and the next turn resends the full bounded history — while a frame past the raised limit still fails the turn. Limit validation happens before the stream parser opens, so a caller error surfaces as a plain error rather than being relabeled as a protocol failure. When a resource limit still fails the stream, the bridge logs the structured numbers (`sseCount` and `sseLimit`) through the host warning sink with the fixed diagnostic label and no request or response content. Synthetic tests cover a 1.5 MiB compaction item on a 872,000-token window streaming to a completed turn that publishes the window (the same payload is rejected under the default limits), a 2.5 MiB item on a 272,000-token window completing the turn with the checkpoint withheld and its refusal logged, the aggregate bound refusing a fourth occurrence at the raised limit, the event count rejecting the 4097th event at the default and admitting 10,000 small deltas at a raised count, and invalid or below-floor limit values refused before the stream starts.

Not verified: the failing turn's actual `encrypted_content` size was not measured — the stream died before any capture, and reproduction needs a real-account turn. Which of the parser's checks fired is not established, and no real-account turn has yet exercised the raised limits; a real firing turn carrying a large checkpoint remains the outstanding confirmation. Each further account operation requires separate explicit authorization.
